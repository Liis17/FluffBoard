## Tech Stack

| Область | Технологии | Роль |
|---------|------------|------|
| Frontend | React 19, React DOM, Vite 8, JavaScript | Вход и Kanban-интерфейс |
| Backend | ASP.NET Core minimal API, .NET 10 | Cookie-сессии, API и GitHub-интеграция |
| Локальные данные | SQLite (`Microsoft.Data.Sqlite`) | Кеш пользователей доски и связей идентичностей |
| Внешние данные | GitHub REST API | Источник и место записи задач |
| Качество | Oxlint | Линтинг frontend-кода |

## Компоненты

- [[backend/API]] — работает на `http://localhost:5279`, загружает корневой `.env` (с приоритетом при `--mac`), хранит пользователей локально и публикует защищённое API доски.
- [[backend/GitHubClient]] — от имени сервисного GitHub-аккаунта читает и записывает issues одной репозитории.
- [[frontend/Приложение]] — Vite-клиент, обычно на `http://localhost:5173`; проксирует `/api` и хранит только cookie-сессию, не токен GitHub.
- [[frontend/Доска]] — чистая логика доски: фильтрация, группировка, перенос карточек и метрики.
- `docs/handoff_fluffboard_board/` — дизайн-хендофф редизайна: токены, покомпонентная анатомия, модель состояния и план внедрения. Значения токенов в `frontend/src/index.css` взяты оттуда дословно.
- `CONTEXT.md` — словарь доменных терминов: пользователь доски, GitHub assignee, Telegram identity и задача.

## Сквозной поток: вход и изменение задачи

1. Backend загружает корневой `.env` и в режиме `--mac` отдаёт ему приоритет над окружением процесса, валидирует owner/repository и список пользователей, затем синхронизирует пользователей в SQLite.
2. Пользователь отправляет логин и пароль в `POST /api/auth/login`; backend сравнивает пароль с PBKDF2-хешем и создаёт cookie-сессию.
3. `App` запрашивает `/api/board/issues`, `/statuses`, `/labels` и `/users` через Vite proxy.
4. Backend передаёт запрос `GitHubClient`; тот читает свежие данные GitHub, исключает pull request'ы и выводит из labels статус с приоритетом.
5. При сохранении редактор отправляет POST или PUT в backend со статусом и приоритетом. `GitHubClient` собирает из них служебные labels, синхронизирует state, создаёт/обновляет issue GitHub и возвращает новую версию.
6. Клиент перезагружает доску и раскладывает задачи по выбранной группировке, ничего дополнительно не вычисляя. Перенос карточки — тот же `PUT`, но применённый оптимистично: при отказе GitHub карточка возвращается на место.

## Соглашения

- Одна инсталляция FluffBoard обслуживает одну репозиторию, заданную в `Board__Repository__Owner` и `Board__Repository__Name`.
- Владелец `GitHub__Token` — отдельный сервисный аккаунт с минимальным permission **Issues: Read and write**. Браузер не получает этот токен.
- Локальный пользователь может иметь `GitHubLogin` и `TelegramId`: это одна личность в разных системах. Telegram-авторизация и уведомления остаются будущим расширением.
- Статус и приоритет — GitHub labels, а не отдельное состояние в SQLite.

## Служебные лейблы

У GitHub Issues нет ни статуса, ни приоритета, поэтому оба измерения хранятся служебными labels с префиксом. Альтернатива — поля Projects v2 — отклонена. Соглашение реализовано целиком в [[backend/GitHubClient]], наружу отдаются готовые поля `status` и `priority`.

| Label | Цвет | Название |
|---|---|---|
| `status:todo` | `f59e0b` | К выполнению |
| `status:in-progress` | `2563eb` | В работе |
| `status:done` | `16a34a` | Готово |
| `priority:urgent` | `dc2626` | Срочно |
| `priority:high` | `ea580c` | Высокий |
| `priority:medium` | `ca8a04` | Средний |
| `priority:low` | `64748b` | Низкий |

Цвета взяты из макета редизайна (`docs/handoff_fluffboard_board/01-tokens.md`). Приоритет «Без» отдельного label не имеет — это отсутствие любого `priority:*`.

**Чтение статуса** трёхступенчатое, иначе закрытые задачи без label уехали бы в «К выполнению»:

1. есть `status:*` label → его ключ;
2. иначе issue закрыт → `done`;
3. иначе → `todo`.

**Запись** синхронизирует состояние в обе стороны: статус «Готово» закрывает issue, любой другой переоткрывает. Источник правды — label; правило 2 работает только для задач без него, поэтому бэкфилл на уже существующие задачи не нужен.

**Инварианты.** У задачи максимум один `status:*` и один `priority:*`. При нарушении (ручная правка в GitHub) labels сортируются по каноническому порядку и берётся первый — для приоритета это самый высокий уровень; следующее сохранение из UI нормализует.

**Пользовательские колонки** называются литералом, как ввёл пользователь: `status:На проверке`, отображаемое имя — текст после префикса. У трёх встроенных статусов ключи латинские, потому что `done` нужен стабильный ключ. Цвет колонки берётся из hex самого label, поэтому второго источника правды для цвета нет. Порядок колонок: три встроенных фиксированно, пользовательские после них по алфавиту — у labels GitHub нет порядка, поэтому ручное переупорядочивание колонок в этой схеме недоступно и потребует хранения порядка в [[backend/BoardDatabase]].
