## Компоненты

- [[backend/API]] — работает на `http://localhost:5279`, загружает корневой `.env` (с приоритетом при `--mac`), хранит пользователей локально и публикует защищённое API доски.
- [[backend/GitHubClient]] — от имени сервисного GitHub-аккаунта читает и записывает issues одной репозитории.
- [[frontend/Приложение]] — Vite-клиент, обычно на `http://localhost:5173`; проксирует `/api` и хранит только cookie-сессию, не токен GitHub.
- [[frontend/Доска]] — чистая логика доски: фильтрация, группировка, перенос карточек и метрики.
- [[frontend/Разметка]] — чистая логика описания задачи: панель разметки, вставка картинки и рендер markdown.
- `docs/handoff_fluffboard_board/` — дизайн-хендофф редизайна: токены, покомпонентная анатомия, модель состояния и план внедрения. Значения токенов в `frontend/src/index.css` взяты оттуда дословно.
- `CONTEXT.md` — словарь доменных терминов: пользователь доски, GitHub assignee, Telegram identity и задача.
- [[Развёртывание]] — один Docker-образ с backend и собранным клиентом, сборка на self-hosted раннере и compose для сервера.

## Сквозной поток: вход и изменение задачи

1. Backend загружает корневой `.env` и в режиме `--mac` отдаёт ему приоритет над окружением процесса, валидирует owner/repository и список пользователей, затем синхронизирует пользователей в SQLite.
2. Пользователь отправляет логин и пароль в `POST /api/auth/login`; backend сравнивает пароль с PBKDF2-хешем и создаёт cookie-сессию.
3. `App` запрашивает `/api/board/issues`, `/statuses`, `/labels`, `/users` и `/assignees` через Vite proxy.
4. Backend передаёт запрос `GitHubClient`; тот читает свежие данные GitHub, исключает pull request'ы и выводит из labels статус, приоритет и платформы.
5. Открытая задача догружает `/issues/{number}/comments` — комментарии есть только у неё, поэтому в общую загрузку доски они не входят.
6. При сохранении редактор отправляет POST или PUT в backend со статусом, приоритетом и платформами. `GitHubClient` собирает из них служебные labels, синхронизирует state, создаёт/обновляет issue GitHub и возвращает новую версию.
7. Клиент перезагружает доску и раскладывает задачи по выбранной группировке, ничего дополнительно не вычисляя. Перенос карточки — тот же `PUT`, но применённый оптимистично: при отказе GitHub карточка возвращается на место.

## Соглашения

- Одна инсталляция FluffBoard обслуживает одну репозиторию, заданную в `Board__Repository__Owner` и `Board__Repository__Name`.
- Владелец `GitHub__Token` — отдельный сервисный аккаунт с минимальным permission **Issues: Read and write**. Браузер не получает этот токен.
- Локальный пользователь может иметь `GitHubLogin` и `TelegramId`: это одна личность в разных системах. Telegram-авторизация и уведомления остаются будущим расширением.
- Статус, приоритет и платформы — GitHub labels, а не отдельное состояние в SQLite.
- В development клиент и backend — два процесса, в production — один: собранный бандл лежит в `wwwroot` рядом с backend, поэтому origin у страницы и у API общий, а CORS нужен только Vite. См. [[Развёртывание]].

## Служебные лейблы

У GitHub Issues нет ни статуса, ни приоритета, ни платформы, поэтому все три измерения хранятся служебными labels с префиксом. Альтернатива — поля Projects v2 — отклонена. Соглашение реализовано целиком в [[backend/GitHubClient]], наружу отдаются готовые поля `status`, `priority` и `platforms`.

| Label | Цвет | Название |
|---|---|---|
| `status:planning` | `7c3aed` | Планирование |
| `status:todo` | `f59e0b` | К выполнению |
| `status:in-progress` | `2563eb` | В работе |
| `status:testing` | `0891b2` | Тестирование |
| `status:done` | `16a34a` | Готово |
| `status:deferred` | `64748b` | Отложено |
| `priority:urgent` | `dc2626` | Срочно |
| `priority:high` | `ea580c` | Высокий |
| `priority:medium` | `ca8a04` | Средний |
| `priority:low` | `64748b` | Низкий |
| `platform:backend` | `1d76db` | Бэкенд |
| `platform:web` | `688b0b` | Веб |
| `platform:windows` | `8644f4` | Windows |
| `platform:mac` | `475569` | macOS |
| `platform:android` | `6aa218` | Android |
| `platform:iphone` | `0891b2` | iPhone |

Порядок статусов в каталоге — это порядок колонок доски, то есть путь задачи слева направо. «Отложено» стоит за «Готово»: оно вне этого пути, а не следующий его шаг. Закрывает issue только «Готово», поэтому отложенная задача остаётся открытой в GitHub.

Цвета статусов и приоритетов взяты из макета редизайна (`docs/handoff_fluffboard_board/01-tokens.md`); у «Планирования», «Тестирования» и «Отложено» цвета взяты из палитры пользовательских колонок оттуда же. Цвета четырёх первых платформ унаследованы от лейблов, которые в репозитории уже существовали неформально до переименования в служебные. Приоритет «Без» отдельного label не имеет — это отсутствие любого `priority:*`; отсутствие платформы устроено так же.

**Число значений** у измерений разное, и это принципиально:

| Измерение | Значений у задачи | Каталог |
|---|---|---|
| статус | ровно одно | открытый: пользователь заводит свои колонки |
| приоритет | не больше одного | закрытый: 4 уровня плюс «Без» |
| платформа | сколько угодно | закрытый: 6 платформ |

Платформа многозначна потому, что так устроены сами задачи: одна и та же работа бывает нужна и на бэкенде, и в клиенте. У закрытого каталога есть следствие: неизвестный ключ (`platform:linux`, поставленный руками в GitHub) при чтении отбрасывается, а следующее сохранение из UI снимет и сам label — показать такую платформу всё равно негде, колонки строятся по каталогу. Запись такого ключа через API даёт 400.

**Чтение статуса** трёхступенчатое, иначе закрытые задачи без label уехали бы в «К выполнению»:

1. есть `status:*` label → его ключ;
2. иначе issue закрыт → `done`;
3. иначе → `todo`.

**Запись** синхронизирует состояние в обе стороны: статус «Готово» закрывает issue, любой другой переоткрывает. Источник правды — label; правило 2 работает только для задач без него, поэтому бэкфилл на уже существующие задачи не нужен.

**Инварианты.** У задачи максимум один `status:*` и один `priority:*`. При нарушении (ручная правка в GitHub) labels сортируются по каноническому порядку и берётся первый — для приоритета это самый высокий уровень; следующее сохранение из UI нормализует. К `platform:*` инвариант не относится: их может быть сколько угодно, и порядок в ответе — канонический порядок каталога, а не порядок labels в GitHub.

**Пользовательские колонки** называются литералом, как ввёл пользователь: `status:На проверке`, отображаемое имя — текст после префикса. У встроенных статусов ключи латинские, потому что `done` нужен стабильный ключ. Цвет колонки берётся из hex самого label, поэтому второго источника правды для цвета нет. Порядок колонок: встроенные фиксированно в порядке каталога, пользовательские после них по алфавиту — у labels GitHub нет порядка, поэтому ручное переупорядочивание колонок в этой схеме недоступно и потребует хранения порядка в [[backend/BoardDatabase]].
