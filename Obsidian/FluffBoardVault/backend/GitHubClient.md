# GitHubClient

Parent: [[Index]]

## Назначение

`GitHubClient` — единственная граница backend с GitHub REST API. Он получает актуальные issues и labels, создаёт и обновляет issues от имени сервисного аккаунта. Здесь же целиком живёт [[Архитектура#Служебные лейблы|соглашение о служебных лейблах]]: наружу класс отдаёт статус и приоритет готовыми полями, поэтому про префиксы не знает больше никто.

## Ключевые методы

| Метод | Описание |
|---|---|
| `GetIssuesAsync(...)` | Загружает все страницы issues, исключает pull request'ы и возвращает номер, заголовок, body, state, URL, labels, assignees, status и priority. |
| `GetLabelsAsync(...)` | Загружает все labels репозитория, включая служебные. |
| `GetStatusesAsync(...)` | Собирает колонки доски из labels с префиксом `status:`. Три встроенных статуса возвращаются всегда, даже если labels ещё не созданы, иначе свежий репозиторий остался бы без колонок. |
| `CreateIssueAsync(...)` | Создаёт задачу. Задачу в статусе «Готово» закрывает вторым запросом: создать issue сразу закрытым GitHub не позволяет. |
| `UpdateIssueAsync(...)` | Обновляет поля задачи и синхронизирует state со статусом. |
| `EnsureServiceLabelsAsync(...)` | Создаёт отсутствующие служебные labels с каноническим цветом. |
| `IsServiceLabel(...)` | Отличает служебный label по префиксу; используется и при разборе задачи, и при нормализации запроса. |
| `IsKnownPriority(...)` | Проверяет ключ приоритета при валидации запроса. |
| `ToIssue(...)` | Делит labels на служебные и обычные, выводит статус и приоритет. |
| `Configure(...)` | Настраивает base URL, обязательные GitHub-заголовки и Bearer token. |
| ~~`EnsureWorkflowLabelsAsync(...)`~~ | (удалён: 2026-07-25) Создавал labels `todo`, `in-progress`, `done` без префикса, предварительно вычитывая все labels репозитория. |

## Важные детали

GitHub включает pull request'ы в issues-ответ; записи с полем `pull_request` исключаются. Пагинация не зависит от конкретного параметра: клиент переходит по URL из `Link: rel="next"`, поэтому работает и с page-, и с cursor-based выдачей GitHub. Токен берётся только из `GitHub__Token` на backend.

`EnsureServiceLabelsAsync` не вычитывает labels репозитория: статус присутствует в каждой записи, поэтому такой запрос стал бы постоянным. Вместо этого label создаётся сразу, а `422 already_exists` означает, что он уже на месте; подтверждённые labels кешируются на время жизни процесса в статическом словаре — сам клиент транзиентный, инстансное поле не переживёт запрос. Канонический цвет — косметика, поэтому любая другая ошибка создания label не роняет запись задачи: GitHub назначит собственный цвет при применении, а настоящие проблемы вроде нехватки прав у токена всплывут на записи самой задачи.
