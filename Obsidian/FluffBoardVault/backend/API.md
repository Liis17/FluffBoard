# API

Parent: [[Index]]

## Назначение

ASP.NET Core backend FluffBoard: аутентифицирует пользователей локальной доски, работает с одной настроенной GitHub-репозиторией и синхронно создаёт, редактирует и читает её issues.

## Файлы

- `backend/Program.cs` — конфигурация приложения, cookie authentication, CORS и minimal API.
- `backend/GitHubClient.cs` — typed GitHub REST client; читает issues и labels, создаёт и обновляет issues.
- `backend/BoardDatabase.cs` — SQLite-хранилище пользователей и PBKDF2-хеширование пароля.
- `backend/BoardOptions.cs` — настройки репозитория и пользователей из конфигурации.
- `backend/DotEnv.cs` — загружает переменные окружения из корневого `.env`; в режиме `--mac` его значения имеют приоритет над окружением процесса.
- `backend/backend.csproj` — web SDK и `Microsoft.Data.Sqlite`.
- `backend/backend.http` — примеры входа и запросов доски.

## Маршруты

| Маршрут | Доступ | Назначение |
|---|---|---|
| `GET /api/hello` | публичный | Legacy-приветствие starter-приложения. |
| `POST /api/auth/login` | публичный | Проверяет учётные данные и выдаёт cookie-сессию. |
| `POST /api/auth/logout` | публичный | Удаляет текущую cookie-сессию. |
| `GET /api/board/me` | пользователь доски | Возвращает текущий профиль. |
| `GET /api/board/users` | пользователь доски | Возвращает участников и их GitHub login для назначения задачи. |
| `GET /api/board/issues` | пользователь доски | Возвращает актуальные issues настроенной репозитории без pull request'ов, со статусом, приоритетом и платформами отдельными полями. |
| `GET /api/board/issues/{number}/comments` | пользователь доски | Возвращает комментарии одной задачи: автор, тело, дата и ссылка. Только чтение. |
| `GET /api/board/labels` | пользователь доски | Возвращает обычные labels GitHub-репозитория для выбора меток; служебные отфильтрованы. |
| `POST /api/board/labels` | пользователь доски | Создаёт обычную метку с цветом из палитры по кругу. |
| `GET /api/board/assignees` | пользователь доски | Возвращает логины, которых GitHub примет исполнителями. |
| `POST /api/board/assets` | пользователь доски | Принимает картинку `multipart/form-data` и возвращает её имя и ссылку. |
| `GET /api/board/statuses` | пользователь доски | Возвращает колонки доски: ключ, отображаемое имя и цвет. |
| `POST /api/board/statuses` | пользователь доски | Создаёт пользовательскую колонку — label `status:<имя>` с цветом из палитры по кругу. |
| `POST /api/board/issues` | пользователь доски | Создаёт GitHub issue. |
| `PUT /api/board/issues/{number}` | пользователь доски | Обновляет заголовок, описание, labels, исполнителей, статус, приоритет и платформы GitHub issue. |

## Важные детали

- Настройки берутся из `.env`: `GitHub__Token`, `Board__Repository__Owner`, `Board__Repository__Name` и массив `Board__Users__N__*`. При обычном запуске корневой `.env` лишь дополняет окружение процесса. Команда `dotnet run --project backend -- --mac` отдаёт приоритет корневому `.env`, а отсутствующие в нём значения берёт из окружения процесса. Реальный `.env` не коммитится; пример — [`.env.example`](../../../.env.example).
- SQLite по умолчанию хранится в `data/fluffboard.db`. При старте учётные записи точно синхронизируются с конфигурацией: добавляются, обновляются и удаляются, если пользователя больше нет в `.env`; пароль сохраняется только как PBKDF2-хеш.
- Все пользователи доски могут управлять задачами. `GitHubLogin` и `TelegramId` относятся к одному локальному пользователю; Telegram ID пока служит только связью идентичностей.
- Исполнителей у задачи может быть несколько, и запрос несёт весь список: GitHub заменяет `assignees` целиком, поэтому передача одного логина стирала остальных. Назначать можно и логин, которого нет среди участников доски — в репозитории такие уже есть.
- Список исполнителей приходит из `GET /repos/:owner/:repo/assignees` — это те, кого GitHub примет. Контрибьюторы для этого не годятся: у части из них нет доступа к репозиторию, назначение такого логина GitHub молча отбрасывает, и задача сохранилась бы без исполнителя.
- Комментарии живут отдельным маршрутом и грузятся по одной задаче: получить их сразу для всей доски GitHub не даёт, а запрос на каждую из сотни задач ради списка карточек не нужен. Маршрута на отправку нет намеренно — доска ходит в GitHub от сервисного аккаунта, и комментарий ушёл бы не от имени автора.
- Вложения описания складываются в ветку `board-assets` через Contents API: публичного API для вложений issue у GitHub нет. Ветка сиротская — первый коммит без родителей и с одним README, поэтому она не выглядит отставшей копией рабочей ветки. Размер файла ограничен 5 МБ, расширения — png, jpg, jpeg, gif, webp; имя файла в путь не идёт, оно остаётся только подписью в разметке. Маршрут отключает antiforgery: сессия живёт в cookie с `SameSite=Lax`, поэтому чужая страница такой POST не отправит.
- Имя пользовательской колонки может быть русским, поэтому её ключ в заголовке `Location` экранируется: заголовки HTTP обязаны быть ASCII, иначе Kestrel рвёт уже успешный ответ.
- GitHub token никогда не передаётся клиенту. Он должен принадлежать отдельному сервисному аккаунту и иметь **Issues: Read and write** в настроенной репозитории.
- Статус, приоритет и платформы хранятся служебными labels — см. [[Архитектура#Служебные лейблы]]. Клиент присылает их отдельными полями `status`, `priority` и `platforms`, а массив labels собирает backend, поэтому присланные клиентом `status:*`, `priority:*` и `platform:*` отбрасываются в `NormalizeLabels`. Поля `state` в запросе нет: статус «Готово» закрывает issue, любой другой — переоткрывает, и второго источника правды для состояния не существует.
- `platforms` — массив: платформ у задачи может быть несколько. `PUT` заменяет задачу целиком, поэтому опущенный `platforms` снимает все платформы, а не сохраняет прежние. Неизвестный ключ платформы даёт 400.
