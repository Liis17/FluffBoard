# FluffBoard

FluffBoard — full-stack Kanban-доска для GitHub Issues на React 19/Vite и ASP.NET Core/.NET 10; задачи и служебные labels хранятся в GitHub, локальные пользователи — в SQLite.

Vault: `Obsidian/FluffBoardVault/` — память о текущем устройстве проекта. Пути исходников в заметках отсчитываются от корня репозитория.

### Чтение и восстановление памяти

- Перед работой прочитай `Index.md` и только заметки, относящиеся к задаче. Проверяй описанное по актуальному коду, конфигурации и документации.
- Перед созданием заметки ищи существующую по назначению, названию и исходникам. Если `Index.md` отсутствует, сначала найди существующие заметки и восстанови навигацию; не считай vault пустым.
- При создании или восстановлении заметки прочитай `references/note-templates.md` навыка; для точечного обновления шаблон не обязателен.
- Проверяй существование заметок и каждого файла `.obsidian/` отдельно. Создавай только отсутствующие; существующие заметки, конфигурацию и пользовательские настройки сохраняй.
- Для `.obsidian/` проверяй `app.json`, `appearance.json`, `core-plugins.json`, `graph.json` и `workspace.json` по отдельности. Шаблоны из `assets/obsidian-config/` навыка копируй только для отсутствующих файлов.

### Содержание и обновление

- Храни текущее устройство значимых компонентов: назначение и границы, публичные контракты, зависимости, потоки, конфигурацию, ограничения и инварианты. Указывай реальные пути исходников и важные символы.
- Описывай контракты по смыслу, не копируй полный код, списки методов и полей или очевидные детали реализации. Причины решений фиксируй только по подтверждённым источникам или словам пользователя; неизвестные причины не выдумывай.
- Обновляй связанную заметку при изменении описанного поведения или общего устройства. `Architecture.md` содержит стек, границы, основные потоки и ограничения. Значимые заметки должны быть достижимы из `Index.md`.
- Удалённые контракты и неверные сведения убирай. Changelog, дневники задач, отчёты по коммитам и датированные записи об удалённых методах не веди.

### Имена и ссылки

- Основные имена заметок — `Index.md` и `Architecture.md`. Файлы и папки доменов называй по-английски, для новых заметок используй PascalCase. В текущем vault уже есть русские имена: при его актуализации переименовывай заметки на месте, сохраняя содержимое, а не создавай английские копии.
- Перед переименованием проверяй backlinks и обновляй wikilinks, встраивания, Markdown-ссылки, пути в `AGENTS.md` и сохранённые пути Obsidian. Внутренние wikilinks должны вести к существующим заметкам; при неоднозначности указывай путь внутри vault.
- Вне vault при работе по этому навыку изменяй только корневой `AGENTS.md`. `CLAUDE.md` не создавай и не изменяй.

## Проверка затронутых компонентов

- Backend: при изменениях API проверь маршруты в `backend/Program.cs`, клиентские вызовы в `frontend/src/api.js` и связанные компоненты `backend/GitHubClient.cs`, `backend/BoardCache.cs` и `backend/BoardDatabase.cs`.
- Frontend: при изменениях `frontend/src/` проверь затронутые представления и использование API-контрактов; клиент использует React 19 и Vite.
- Контракты проекта: HTTP API `/api`, GitHub Issues и labels, схема пользователей SQLite и настройки `Board__*`/`GitHub__*`. Проверь совместимость производителей и потребителей при их изменении.
- Сохраняй обратную совместимость контрактов и пользовательские данные, если задача явно не требует иного. Проверяй только затронутые части и указывай, что осталось непроверенным.

## Архитектурные границы

- Backend использует ASP.NET Core minimal API: HTTP-маршруты находятся в `backend/Program.cs`; интеграция с GitHub — в `backend/GitHubClient.cs`; кэш — в `backend/BoardCache.cs`; пользователи и SQLite — в `backend/BoardDatabase.cs`.
- Сохраняй существующее разделение ответственности, DI и вызовы из React-клиента через `frontend/src/api.js`. Не добавляй общие абстракции без повторного потребителя.
- В разработке Vite проксирует `/api` на backend; production раздаёт собранный клиент вместе с backend. Учитывай оба режима при изменении загрузки клиента или API.

## GitHub API и данные

- GitHub REST API хранит задачи, статусы, приоритеты, платформы и комментарии; изменения формата Issues или labels проверяй также на клиенте и в уже сохранённых репозиториях.
- Сохраняй асинхронную обработку HTTP и SQLite, передачу `CancellationToken` и обработку ошибок внешних запросов.
- `BoardDatabase.InitializeAsync` синхронизирует список локальных пользователей с конфигурацией и удаляет пользователей, отсутствующих в ней. Учитывай это поведение при изменениях конфигурации и работы с SQLite.

## Проверка изменений

- Проверяй минимально достаточный набор: затронутый backend или frontend, связанные API-контракты и тесты соответствующей части.
- Frontend-тесты находятся в `frontend/test/`; целевые команды проекта: `npm test --prefix frontend`, `npm run lint --prefix frontend`, `npm run build --prefix frontend` и `dotnet build backend/backend.csproj`.
- Для исправления бага по возможности добавляй тест, воспроизводящий проблему; для новой значимой логики проверяй ожидаемое поведение и существенные ошибки.
- Не запускай автоматически полную сборку всех частей. Не сообщай, что проверки прошли, если они не запускались; при невозможности проверки укажи причину.

## Безопасность окружения

- SQLite-схема создаётся кодом `backend/BoardDatabase.cs`; отдельный инструмент миграций в проекте не используется. Не меняй рабочую базу и не выполняй миграции без явного разрешения.
- Не запускай `docker compose down -v` и не удаляй Docker-том `fluffboard_data` без явного разрешения: там хранится база пользователей.
- Секреты и реальные настройки находятся в `.env`, `docker/fluffboard/.env` и GitHub Actions secrets. Не выводи, не изменяй и не коммить их без необходимости и разрешения; используй примерные файлы как шаблоны.
- Не останавливай процессы по шаблону имени. Останавливай только процессы, принадлежность которых текущей задаче подтверждена.
- Для проверок используй изолированные данные; не коммить временные файлы, дампы, логи и исследовательские заметки.

## Производительность

- Для изменений горячего пути оцени задержки, память, CPU и число обращений к GitHub API.
- Не блокируй асинхронный код синхронным ожиданием и не добавляй повторные сетевые запросы без необходимости.
- Для React UI избегай ненужных перерисовок и полной переработки списков при небольших изменениях. Не оптимизируй без подтверждённой проблемы.

## Правила работы с Git репозиторием

- Запрещено создавать ветки для работы со своей задачей, всегда работай с текущей веткой, если явно не сказано работать в отдельной или пользователь не попросил создать Pull Request.
- Если большая задача с планом, после каждого завершённого этапа делай коммит со своими изменениями. Пуш не делай без явного запроса; запрос на создание Pull Request разрешает создать нужную ветку и отправить её в remote, если пользователь отдельно не запретил это.
- Перед коммитом проверяй `git diff` и убеждайся, что в коммит попали только изменения текущей задачи. Не перезаписывай чужие незакоммиченные изменения.
- Не применяй `git reset --hard`, `git clean -fd` или force push без явного разрешения.
- Не добавляй в коммиты подписи AI, `Co-Authored-By` или упоминания агента без запроса.
- Сообщение коммита должно кратко и понятно описывать результат и не превышать 200 символов целиком, включая пробелы и переносы строк.
- Если сообщение не помещается в 200 символов, сначала сократи его. Самостоятельные изменения разделяй на логически завершённые коммиты с короткими сообщениями.

## Создание Pull Request

### Когда создавать PR

- Создавай Pull Request только по явному запросу пользователя.
- Запрос на создание PR разрешает создать рабочую ветку и отправить её в remote, если пользователь отдельно не запретил эти действия.
- Если пользователь просит только подготовить PR, не выполняй push и не создавай PR.
- Один PR должен решать одну логически связанную задачу; не смешивай несвязанные исправления, рефакторинг и функции.
- Не создавай дублирующий PR, если для этой задачи уже существует открытый.

### Ветки и коммиты

- Целевая ветка — `main`; это единственная подтверждённая долгоживущая ветка. Не меняй её напрямую ради PR.
- Создавай отдельную ветку от актуальной `main`; подтверждённой схемы именования веток в проекте нет, используй `<type>/<short-description>`.
- В истории используются сообщения с типовым префиксом `feat:`, `fix:`, `docs:`, `ci:` или `test:` без устойчивых scope. Сохраняй этот формат и не придумывай обязательные scope; описания в истории встречаются на русском и английском.
- Название PR кратко описывает результат изменения. Примеры: `feat: добавить фильтр по платформам`, `fix: сохранить исполнителей при обновлении`, `docs: уточнить инструкцию запуска`.
- Не включай в PR чужие незакоммиченные изменения.

### Перед созданием PR

1. Проверь полный diff относительно `main` и убедись, что изменённые файлы относятся к задаче.
2. Проверь корректность изменений и обратную совместимость.
3. Запусти доступные целевые проверки затронутых частей; не запускай автоматически полную сборку всех частей проекта.
4. Убедись, что необходимые изменения в `Obsidian/FluffBoardVault/` внесены.
5. Проверь отсутствие секретов, токенов и временных файлов.
6. Убедись, что PR не содержит случайного форматирования или несвязанных правок.

### Описание PR

Шаблон PR в репозитории не найден. Используй краткую структуру:

**Summary**
- Что изменено и какую проблему решает.
- Основные технические решения.

**Testing**
- Выполненные проверки и их результаты.
- Что не проверено и почему.

**Compatibility & Risks**
- Затронутые frontend/backend части.
- Изменения HTTP API, GitHub Issues/labels, SQLite или конфигурации.
- Ограничения, риски и действия при развёртывании.

**Visual Changes** — только для изменений UI; добавляй скриншоты, а для существенных изменений анимации — короткую видеодемонстрацию, если возможно.

Не добавляй пустые разделы и не дублируй очевидные детали.

### После создания PR

- Убедись, что PR направлен в `main`, и проверь доступный статус GitHub Actions.
- Текущий workflow `.github/workflows/build-fluffboard.yml` запускается вручную или при push в `main`, собирает и публикует Docker-образ; проверок на PR в текущей конфигурации нет. Не утверждай, что workflow прошёл, пока результат не подтверждён в GitHub.
- Если пользователь попросил сопровождать PR, следи за результатами проверок и новыми комментариями после последнего изменения.
- Проверяй замечания автоматических ревьюеров по коду, исправляй подтверждённые проблемы и объясняй техническую причину ложных срабатываний.
- Не выполняй merge без явного разрешения пользователя.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
